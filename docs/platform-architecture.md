# Platform architecture

Status: agreed direction, November 2026. Stage 1 (groundwork) is done. Stage 2 is under way: the first version of the suite shell is built (home page, the tools in frames, host bridge, recent files, suite single HTML and exe); the customer workspace file and passing the risk context directly between tools are still to come. The first new module of stage 4, report review, is built.

## Goal

One suite holding several OT cyber tools, where:

- internally, one file (one HTML or one exe) gives a consultant every tool;
- any tool can still be handed out on its own, for example the assessment tool or the risk assessment tool to a contractor, with nothing else attached;
- tools can work with each other's results (the risk tool's target Security Levels feeding an assessment, or a future report-review module reading an assessment's findings) without depending on each other's code.

The suite is called the **SolutionsPT OT Cyber Suite** ("OT Cyber Suite" where space is short, as in its header).

## Principles

1. **A module is a complete app.** Each tool has its own folder, entry page, tests, single-HTML build and exe build. Nothing about the suite is needed to run it.
2. **The suite is a thin shell.** It finds the modules, shows them side by side, owns the customer workspace file and passes data between modules. It holds no assessment logic of its own.
3. **Modules never call each other's code.** They exchange data through versioned contracts. Two modules can therefore change, ship and be tested independently.
4. **Shared code is copied in, not linked.** One canonical copy lives in `shared/`; a sync step copies it into each module, and a check fails if a module's copy drifts.
5. **One version for everything.** Every file in a release carries the same version number.

## How a module works

Each module folder contains:

- `index.html`, its own `js/`, `data/`, `vendor/` and `css/`, so it runs from `file://` with no server;
- `module.json`, a manifest: id, product name, entry page, which tests to run, and how its exe self-test works;
- its own `LICENCE.txt` and copies of the shared files, kept in step by `tools/sync-shared.ps1`;
- `scripts/test-*.html`, its headless test pages, run by `tools/run-tests.ps1 -Module <id>`.

From stage 2, the manifest also declares what the module **produces** and **consumes** in contract terms. For example, the risk tool produces `spt-risk-context`, and the assessment tool's 62443-3-3 instrument consumes it.

### Running standalone or inside the suite

Inside the suite, each module runs in its own frame. The two existing tools both define the same global object and load the same libraries, so they cannot share one page. The frame also guarantees a module behaves the same in both settings.

**The suite shell (first version, built).** A home page with a card per tool, "Recent files", "Getting started" (what each tool is for, and its guided tour) and "What's new" (the newest `docs/releases/v*.md`), plus the version and the licence pop-up. Opening a tool shows it in a frame under a slim bar: home, the tool's name, and a switcher for the other tools. A tool's frame is created the first time it is opened and then stays alive, hidden, when another is shown, so switching never loses work. Each tool still saves and loads its own project file from its own header; the shared customer workspace file is a later step.

**Where a tool's page comes from, and the origin rules that follow.** Chromium gives every `file://` page an origin of its own, so:

| Build | Frame | Origin | File dialogs in the tool | Shell can reach into it |
|---|---|---|---|---|
| Folder (developer): `platform/index.html` | `../modules/<id>/index.html` | different from the shell | refused by the browser; Save downloads, Load uses the file input | no (postMessage only) |
| Suite single HTML and exe | the tool's own single-HTML build, carried in the suite file and given to the frame as `srcdoc` | the shell's | yes, as standalone | yes |

- The single-file build carries each tool's own single HTML (byte for byte the file that ships on its own) gzipped and base64-encoded in a `<script type="application/x-spt-payload">` element, and the assessment tool's tour built from `tour.html` the same way. The shell unpacks one with `DecompressionStream` the first time it is opened. The suite file is about 6 MB with the three tools and the assessment tour inside.
- A `blob:` URL does not work: from a `file://` page Chromium will not run a `blob:` page in a frame at all. `srcdoc` and `about:blank` with `document.write` both share the parent's origin; `srcdoc` is used because it gives the tool a clean `about:srcdoc` address rather than the shell's.
- localStorage is shared by every `file://` page, so the tools' autosave and the `ot-theme` setting work the same inside and outside the suite (in the exe, each exe has its own storage).
- A tool decides whether it can use the file dialogs by checking whether it can see the top page (`inForeignFrame()` in each tool); framed by a page of another origin it behaves as in a browser without the dialogs. Whatever the reason, a save dialog refused for security reasons (a `SecurityError`) falls back to a download, so saving never fails.

**The host bridge** (`shared/host-bridge.js`, synced into each module as `js/host-bridge.js`) is the only connection, and it is optional: every call a module makes is guarded (`if (window.App.HostBridge)`), and standalone `App.HostBridge.hosted` is false and every method does nothing. The shell names each frame `spt-suite:<launch JSON>` (`{ module, frame, tour }`), so a module knows before its own code runs that it is hosted and how it was opened; the risk tool's tour is opened this way (`tour: true`), since a page given as `srcdoc` has no query string. Messages are postMessage objects with `protocol: "spt-suite/1"`:

| From | Type | Data | When |
|---|---|---|---|
| tool | `ready` | product, version, number, title, dirty, reopen, theme | the tool has started |
| tool | `dirty` | dirty | unsaved changes appear or are saved (drives the bar and the close warning) |
| tool | `recent` | action (`save` or `open`), name, label, hasHandle, when | a project file was saved or opened |
| tool | `theme` | theme | the tool's own theme toggle was used |
| shell | `theme` | theme | follow the suite's theme |
| shell | `open-recent` | name, label | reopen a file from Recent files |

**Recent files** live in the shell's localStorage (`spt-suite:recent:v1`, newest first, at most 12, one entry per tool and file name): tool, file name, customer or project label, saved or opened, and when; never the contents. Where the browser gave the tool a file handle, the bridge keeps it in the tool's own IndexedDB (`spt-suite-recent`). Choosing a recent file opens its tool and sends `open-recent`: with a handle, the tool offers "Reopen" and the click inside the tool's frame asks for access (a browser only grants file access in answer to a click on that same page, and a click in the shell does not count for the frame); without one, the tool highlights its Load button and names the file.

**Unsaved work.** Each tool's own `beforeunload` warning still runs in its frame, and the shell adds its own while any tool reports unsaved changes (a frame that was never clicked in may not be allowed to warn). The bar and the home page cards mark tools with unsaved changes. In the exe, Electron raises `will-prevent-unload` for the shell page or a tool's frame alike, and `packaging/electron/app/main.js` asks the question; the suite's exe self-test checks both paths.

Later in stage 2 the bridge also carries the tool's data to the shell for the customer workspace file, and contracts (the risk context) between tools directly.

## Data

### Customer workspace file (stage 2)

In the suite there is one file per customer. Each module's data sits in its own section, in the module's own format. This extends what the assessment project file already does, holding several assessments per customer.

A contractor's standalone project file can be imported into a workspace section and exported back out, so work moves between a contractor and the suite without conversion.

### Contracts

A contract is a JSON definition in `contracts/` with a schema string such as `spt-risk-context/1.4`, the shape, an example and the list of schema versions importers accept. The rules:

- the producer writes the current schema; consumers accept the listed versions and reject unknown ones;
- a change of shape bumps the schema string, so a mismatch fails loudly rather than silently;
- each module keeps a synced copy, so it can still read and write the contract standalone.

| Contract | Producer | Consumer | Carries |
|---|---|---|---|
| `spt-risk-context/1.4` | risk tool | assessment tool (62443-3-3) | target Security Levels per zone, and the risk register as context |
| `spt-review-pack/1.0` | assessment tool, risk tool | report review tool | the report as the client will read it, the engagement behind it, earlier rounds' comments |
| `spt-review/1.0` | report review tool | assessment tool, risk tool | one reviewer's comments, checklist and verdict |

Report review reads a pack's text from the generated Word file (`shared/docx-blocks.js`, using the exporter's own tags for section keys), so a reviewer sees what the client gets: the file is the source of truth, which is also why the assessment tool's Issue check counts red prompts from the build. See [report-review.md](report-review.md).

## Builds and releases

`tools/build.ps1 -Module <id> -As html|exe|both` builds one module, and `-Module suite` builds the suite the same way (`packaging/module-info.ps1` reads `platform/suite.json` for it). The suite's single HTML builds each tool's single HTML first and carries it; its check page is `packaging/single-html/check-single-html-suite.html` and its exe self-test `packaging/electron/app/selftest-suite.js`. From stage 3 the choice of modules is made at build time; for now the suite carries every tool listed in `suite.json`.

`tools/release.ps1` builds one release from one commit. It refuses to start with uncommitted changes, an existing tag, drifted shared files, out-of-date suite home page data or a missing `docs/releases/v<x.y.z>.md` (one release notes file per version, used for the GitHub release and the suite's What's new). It runs each module's tests, builds and checks every file, stages the files with `SHA256SUMS.txt` in `dist\<version>\` and tags `v<x.y.z>`. A release carries:

| File | For |
|---|---|
| SolutionsPT OT Cyber Suite HTML / exe | internal use: every tool in one file |
| OT Cyber Assessment Tool HTML / exe | the assessment tool on its own |
| OT Cyber Risk Assessment Tool HTML / exe | the risk tool on its own |
| OT Cyber Report Review Tool HTML / exe | the review tool on its own, for a reviewer who needs nothing else |
| `SHA256SUMS.txt` | checksums |

The version is shown in each tool and recorded in saved project files. It never appears in Word or Excel exports.

### Branches

- `main` always holds tested, releasable code; releases are tagged from it.
- Work in progress goes on short-lived feature branches (for example `feature/platform-shell`), merged when its tests pass.
- There are no per-module branches: modules are folders on `main`, so a shared fix reaches every module at once.
- A release branch is created only if an old version ever needs a patch after `main` has moved on.

## Known gaps

- The risk tool's notice says "see LICENCE.txt", but its single HTML and exe have no file beside them (the licence is only embedded as a comment). It needs a licence pop-up like the assessment tool's. (Inside the suite, the suite's licence pop-up covers both tools.)
- In the folder build of the suite the tools cannot save in place (the browser refuses file dialogs in a frame of another origin), so Save downloads a new copy each time. The suite's home page says so in that build.
- Risk tool project files do not record which version saved them, unlike assessment project files.
- The example in `contracts/risk-context-interchange.json` still shows `generatedBy: spt-risk-tool/0.2`; the risk tool now writes the suite version there.

## Decisions

- The suite's product name is the SolutionsPT OT Cyber Suite (November 2026). It titles the suite's window and its files.
- The suite single HTML keeps each module's own copy of the vendor libraries: it carries each tool's own single HTML unchanged, so a tool behaves identically in and out of the suite. Gzipping keeps the suite file smaller than the assessment tool alone.
