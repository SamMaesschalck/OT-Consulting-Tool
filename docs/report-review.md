# Report review

A team reviews reports and engagements through the tools rather than by marking up Word files, in line with the rule that changes are made in the tool, not in Word. It works fully offline, with no server: the author sends a pack, each reviewer saves their own small review file, and the author imports those files. Comments merge, so reviewers can never overwrite each other.

## For a reviewer

1. Open the pack in the **OT Cyber Report Review Tool** (Load, or drag it onto the page). You will be asked for your name once; the browser remembers it. You can cancel that question; it comes back when you add a comment or save. If the author added a note or a needed-by date when sending, it shows in a quiet panel on Report and Summary. Opening the Word or Excel report, or a PDF of it, in place of the pack says so.
2. **Report** shows the Word report as the client will read it. Click any paragraph, heading or table to comment; click a table cell to comment on that cell. Choose a severity (must fix: wrong, misleading or not fit to send to the client, and the author's Issue check warns while any are open; should fix: weakens the report, change it unless there is a good reason not to; suggestion: the author can take it or leave it), and tick Suggest wording to propose text, which starts from what is there. Text the report still prints in red is flagged "Prompt left in". The sections on the left count your comments; in a narrow window a Go to section list does that job. Ctrl+F, or the find box above the report, finds words in the report. The bar holding the find box (and, in a narrow window, Go to section) stays at the top as you scroll.
   A comment you are still writing is kept: a click on another paragraph asks you to add or cancel it first, and on another page a bar leads back to it. Delete removes a comment at once; Undo appears for a few seconds. Tick a section in the outline to mark it read (in a narrow window, the Read tick beside Go to section marks the section at the top of the report); that stays in your browser and only tells you how far you have got.
3. **Engagement** shows what is behind the report: each item's answer, target, evidence, notes and plan, and the basis of assessment. Filter to findings, or to items with no evidence, and comment on any of them. A suggestion here is for one field of the item. Each pack names the fields its own way: a risk pack shows the threat source, risk acceptance and disposition, not evidence, notes and priority, leaves out the fields it does not have, and adds likelihood, impact, affected FRs, residual rating and the suggested target levels as extra rows. The search narrows the list as you type, and a link above the list goes to the basis of assessment.
4. **Checklist** has questions for every report and for this type of report. Answer Yes, No or N/A, with a note if there is anything to say.
5. **Automatic checks** lists what a machine can find, with the checks that found something first and the clean ones folded into one card. Each line can take you to the place, be made into a comment, or be dismissed.
6. **Previous round** appears from round 2. It shows what was said last time, what the author did and why, and where each point is now: in which section, and what the text reads now, with the words taken out and put in marked. Go to takes you there. On the Report page an earlier comment sits beside its text even after the author rewrote it, marked "Text changed since round N", or on its section heading when nothing close is left. Confirm a fix you have checked, accept a Won't change reason, or raise the point again, one or the other: a point raised again is put on the text as it reads now, can carry suggested wording, and stays linked to the earlier comment. To change your mind, take the confirmation back, or delete the comment you raised.
7. **Summary and verdict**: choose Approved, Approved with comments, Changes requested or No verdict yet, then **Save my review file**. Send that file to the author by shared folder or email. Summary shows what is left (checklist, checks, earlier comments looked at, sections read), each going to its page, and where the last save went. Print or save as PDF gives a printout of your review: who, which round, the verdict, every comment in the order the report prints it, from round 2 what became of each earlier comment (confirmed fixed, reason accepted, raised again or not looked at), and the checklist. It is a working note, never part of the report. In the suite, after a save, Summary also offers to give the file straight to the author's tool.

Reviewers in the same round work independently: each sees the others' comments only in the next round's pack.

To carry on later, open the pack and your review file, together or in either order: a review file opened first waits for its pack, and reopening the pack alone points at the review file this browser saved for it. Save then writes back to the same file. If the browser closes unexpectedly, opening the pack again offers your unsaved work, and opening your review file keeps on offer whatever it does not already hold: Restore adds it to the file. Opening a review file over unsaved comments asks first, and adds them to the file rather than dropping them. Open only your own review file: if you open a colleague's, or any named file in a browser that does not know your name yet, you are asked whether you are them; if not, their comments are shown read only beside yours, and your comments and Save stay in your own file. If you carry on as them, what you had not saved goes under their name with the rest of the file, and a later change of name leaves the comments the file already held under their name unless you say they are yours. Unsaved work another reviewer left in this browser is offered under their name, and Restore asks the same question. The header shows whose review is open, and so does the Report page. The demo keeps nothing (no autosave, no Recent files entry, no close warning); a real pack opened in the tour's window is treated as real work.

## For an author

### In the assessment tool

The **Review** card is on the report page, next to the Issue check. It is not a report section and never reaches Word or Excel.

1. **Send for review** runs the Draft build of the per-target documents an export would write, and saves a pack. Each site's document carries its own progress section when the baseline names that site, whichever site is selected. The organisation-wide roll-up across sites is not packed: review each site's assessment, and the export dialog says the roll-up has not been reviewed. Before sending you can add a note and a needed-by date for the reviewers (**Add a note for the reviewers**); they see them in the review tool, and they never reach Word or Excel. Give the pack to each reviewer, and save the project afterwards. In the suite, the card then offers to open the pack in the Report Review Tool, so you can see it as a reviewer will.
2. **Import review files** takes several files at once. Importing the same file twice changes nothing, and a reviewer's later save of the same comment wins. If you sent a pack from a copy of the project you then closed without saving, import the pack file first, then the review files: the pack is put back on this assessment's rounds. A review file for another assessment in the same project says which one to switch to. A file the reviewer saved again under another name says whose it was. In the suite, a review file the reviewer gives to this tool, or one you drop on it, is imported in the same way.
3. Each comment shows the reviewer, severity (hover for what it means), what it is on, and any suggested wording, with the words changed marked and the full wording one click away. Comments are grouped by section, and engagement comments by target and group, so two zones never share a heading; with many comments the groups start closed. Filter by status, severity and reviewer. A comment the reviewer raised again says which round it came from, what was said then, and links to the earlier comment. Each reviewer's line shows their whole checklist ("7 of 9 answered, 1 no", with every answer and note) and the automatic checks they dismissed.
4. **Go to** goes to the section's card, or where that text is edited: the engagement details for document control, the basis register, the consultant input, the progress card, the item behind a finding, or the results or roadmap cards. Text written from the framework says it is only in the Word report, naming the section. After Go to, **Back to the comment** returns to it, from whichever page Go to took you to. Reply, **Resolve**, or **Won't change** with a reason, which the reviewer sees next round. Item comments follow a renamed site or zone (they carry its id).
5. **Accept** puts suggested wording in the tool where the text can be changed there, rebuilds the Word document to check it is really in it, and undoes it if not. Otherwise you get **Copy** and Go to, with the reason. Accepting into a section's opening rewrites the whole run of paragraphs that open it, with the one changed, as plain paragraphs: any emphasis in that run goes. An accepted change can be undone from the comment (**Undo the accepted wording**) unless the text has been edited since. Reopen opens the comment again and leaves the text as it is. Changes to sections that only the Word report has are listed on the report page (**Changes to sections only in the Word report**), each with Back to the generated version.
6. An open comment that no longer matches the report is marked "No longer matches the current report". It is not lost. A closed comment is not marked. If the reviewer changes what a comment you closed says, the import opens it again and says so, and the comment shows your earlier reason.
7. When an approval comes in, the card offers to fill in **QA review by** with the reviewer's name. It asks first, and asks again before replacing a different name.
8. When you have made your changes, **Send for review** again. The round goes up when the content has changed or a review has come back; otherwise the pack is the same round, so a reviewer's file stays good. The new pack carries every comment's status and replies.

The Issue check and the export dialog warn when the report is not reviewed, when changes are requested (including by a reviewer who asked for changes in an earlier round and has not reviewed the latest), when must-fix comments are open, and when it has changed since approval. If QA review by is filled in and no round was ever sent, the review is taken as done outside the tools and there is no not-reviewed warning. The export dialog also says when the organisation-wide report, or a whole-engagement report with fewer zones ticked, is not what the reviewers read. They only warn: Final is never blocked by a review, so a lone contractor with only a standalone tool is not stuck. Filling in the document control fields at issue does not count as a change.

### In the risk tool

**Peer review**, in the sidebar, has the same Send for review (with the note and needed-by date) and Import review files, with the comments list on its own page. A pack sent from a copy of the project that was never saved is put back in the same way: import the pack file, then the review files (a risk pack for the same client and system under consideration). The pack holds both Word reports (detailed and high level) and the zones and threats behind them; with no zones or conduits yet it holds only the high-level report. The risk pack names the item fields its own way (Threat source, Risk acceptance, Countermeasures addressing this threat, Disposition), with band and disposition names rather than codes, and adds likelihood, impact, affected FRs, residual rating and the SL-T suggestion and justification as detail rows.

**Accept** works as in the assessment tool for a section's heading and the wording that opens it, in the report the comment is on (found by its title, then its `documentIndex`): the overrides are per report, because same-named sections say different things. The Word document is rebuilt to check the wording is really in it, and the change is undone if not. An accepted heading or opening can be undone from the comment, unless the section has been edited since. Other text is Copy and Go to, with the reason. **Go to** takes you to the section on the **Report** page, in that report, or scrolls to and highlights the threat, or the zone's or conduit's target levels card. Renaming a zone keeps its comments attached.

The risk tool has no Issue check or Draft and Final. Once a review has started, the Word downloads (both reports) and the Excel download ask once when changes are requested, must-fix comments are open, a sent round has had no review back, or the report has changed since approval; the high-level download leaves out the zone completeness list. The Report, Review & export and high-level report pages show the same warnings in a Peer review card, and the Peer review page refreshes its list as soon as the reports are rebuilt. None of it ever blocks a download. The Engagement details card has a **QA review by** field, printed in document control in both Word reports, and an approval offers to fill it in as in the assessment tool. Recording the asset owner's sign-off is not a change since approval.

## What is stored where

| What | Where | Holds |
|---|---|---|
| Review pack (`spt-review-pack`) | a file the author saves | the client's report text and images, the engagement behind them, earlier comments, and the author's note to the reviewers when there is one. It contains client data: handle it like the project file. |
| Review file (`spt-review`) | a file each reviewer saves | that reviewer's comments with the short quotes they are about, checklist answers and how many questions there were, dismissed checks and what each said, verdict. The quotes are client text, so handle it the same way. |
| The review, on the author's side | the assessment in the project file (`assessment.review`), or the risk project (`project.review`) | rounds (with the note sent and the pack's names for the item fields), the files imported (with each checklist and dismissed check), each comment with its status, reason, replies, and what an Accept replaced so it can be undone. Absent until a review starts; older files still load. Each assessment has its own. Never exported to Word or Excel: the assessment tool's exporters are given the engagement projection, which it is not on, and the risk tool's never read it. |
| Reviewer's name, list of names to look for, sections ticked as read | the reviewer's browser (`spt-review:reviewer:v1`, `spt-review:names:v1`, `spt-review:read:v1:<pack id>`) | never put in a review file |
| Unsaved review work | the reviewer's browser (`spt-review:autosave:v1:<pack id>`) | the review only, not the pack; cleared on save or Discard, and kept and offered again while it holds work the review file you open does not |
| Review file names seen for a pack | the reviewer's browser (`spt-review:seen:v1:<pack id>`) | the pack's and the review file's names, the save date and the reviewer's name, to point at the right file; never content |

## Which text accepts a suggestion

In the assessment tool:

| The comment is on | Goes into | Otherwise |
|---|---|---|
| A section's heading | the section's title (`reportCustom[key].title`) | not if the heading is a target's name, or is built from one, as it would apply to every target |
| A paragraph of a narrative field the consultant wrote (exposure, priorities, method) | that line of the field | |
| A line of the proposed next steps | the next steps, made from all the lines as printed if they were still scaffolded | not if they differ between documents |
| A paragraph or table cell that holds an evidence, notes, owner, action or impact field | that field on that item | not if the same wording is on more than one item |
| An item comment that names a field | that field; if the field does not print in Word, the change stands and the message says so | not if the field has changed since the review, or the site or zone it is on can no longer be found |
| A paragraph in a section's opening run | `reportCustom[key].prose`, the whole run with the one paragraph changed | not if the section opens differently per zone, as a rewrite would replace all of them |
| Anything else: generated text, results tables, framework text | Copy and Go to | |

Each of these can be undone from the comment, unless the text has been edited since it was accepted.

In the risk tool, in the overrides of the report the comment is on (`project.reportCustom.detailed` or `.highLevel`):

| The comment is on | Goes into | Otherwise |
|---|---|---|
| A section's heading | the section's title | not a zone's or conduit's own heading, which is a name: rename it where it is entered. Not a heading repeated per zone ("Justification for ..."), as it would change them all: use Edit on the Report page, which keeps each zone's name |
| A paragraph in a section's opening run | `reportCustom.<report>[key].prose`, the whole run with the one paragraph changed | not a section repeated per zone, as a rewrite would replace all of them |
| Anything else: threat registers, tables, the sign-off, text after a table, the zones and threats behind the report | Copy and Go to | |

Both can be undone from the comment, unless the section has been edited since.

## The automatic checks

They run on the pack, in `modules/report-review/js/checks.js`. A false alarm costs trust, so each is written to be precise.

| Check | What it finds |
|---|---|
| Red prompts left in | exactly what the Issue check counts |
| Em or en dashes | in the client's text, leaving out a cell holding only a dash, and a lone dash for one side of a rating in a cell (as the risk register prints for a likelihood or impact not yet set): both are the house mark for empty, and the unrated threat is reported by Items not answered |
| Internal wording | "the tool", "this tool", "scaffold", "placeholder", "structured prompt", "band arithmetic", "rolled up from", "lorem ipsum", TODO, TBC, TBD, FIXME, as whole words and not in red prompts |
| A demo or other client's name | the demo clients' names, and any the reviewer adds, in the report and the engagement data; never the report's own client, site or consultant, when that holds the name as whole words |
| Client name missing or inconsistent | not set; not printed in a document; printed with different capitals (all capitals is styling, and not flagged) |
| Findings with no evidence | items whose status is finding, with nothing in the pack's evidence field (named as the pack names it); not on a risk pack, where the field is the threat source |
| Items not answered | one line per item, or one per target above five; in a risk pack, a threat not rated or a zone with no target levels |
| Blank document control fields | named together in one line; QA review by is left out, as an approval is what fills it in |
| Section numbering gaps | numbered level 1 headings (the number printed as its own run) whose number jumps forward |
| Figures that disagree | sentences the exporter generates, for a document covering one target: "the N outcomes below their expected state", "open gaps moved from X to N", "there are N open gaps" against the roadmap, and "N of M outcomes were assessed as achieved" against the items met |
| Risks above tolerable with no disposition | risk packs: a threat above the tolerable risk with no countermeasure, no target level on its affected requirements and no recorded acceptance |
| Target levels with no justification | risk packs: a zone or conduit with target levels set and no justification (the report leaves its section out) |

Each paragraph in a table cell is a result of its own, so dismissing one does not hide another.

Not attempted, because no reliable reading exists: the counts inside results tables and charts; percentages and closeness figures; floor-finding counts; "meeting N of M" per requirement group; maturity profiles; any count in a document covering several targets (the 62443-3-3 report covers every zone in one file); whether a recommendation is any good; whether the tone is right. Those are what the reviewer is for, and the checklist asks.

The checklist (`modules/report-review/data/checklists.json`) has common questions, questions per scoring family and per instrument, and a `skip` list that leaves a family question out for an instrument it does not fit (the CSMS elements question for the CRA and Machinery, for example).

## Contracts

`contracts/review-pack.json` and `contracts/review-file.json` hold the shape, an example and the schemas importers accept. Importers reject anything else with a message naming both schemas, so a change of shape fails loudly.

Within `spt-review-pack/1.0` and `spt-review/1.0` some fields are optional and additive: a file without them loads and shows exactly as before, and a reader that does not know them ignores them. Each contract lists them under `_optional`.

| Contract | Optional field | What it is for |
|---|---|---|
| pack | `engagement.fieldLabels` | what the pack calls each item field; null hides the field |
| pack | `items[].targetId`, `items[].details` | the authoring tool's id for the target, so comments follow a rename; extra read-only rows |
| pack | `request` | the author's note and needed-by date for the reviewers; never in Word or Excel |
| pack | `documents[].blocks[].runs[].c` | a key swatch's colour |
| review file | `checklistTotal`, `dismissedCheckTitles` | how many checklist questions there were, and what each dismissed check said |
| review file | `anchor.targetId`, `anchor.media` | the target's id on an item comment; the image an image comment is on |

A comment raised again (`relatesTo` set) is anchored to where its text is now: the same wording in the current pack, else the nearest match in the same section, else the section heading with an empty quote.
